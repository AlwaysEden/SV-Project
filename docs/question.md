# 질문1
## 지원자가 생각하는 '좋은 코드'에 대해서 정의하고 그렇게 생각하는 이유에 대해서 서술하세요.
나의 코드를 이어받을 사람이 이해하고 유지보수할 수 있는 깔끔한 코드라고 생각합니다. 나의 코드를 이어받는 사람은 비단 타인(후임, 동료 또는 상사 등)뿐만 아니라 몇달 뒤의 나 자신도 포함입니다. 이렇게 자신이 작성하지 않은(또는 기억에 없는) 소스코드를 읽는 일은 매우 고통스럽고 힘든 일입니다. 이때 작성해놓은 소스코드가 '좋은 코드'라면 아래의 장점을 가지게 된다고 생각합니다.

### 1. 자연스럽게 좋은 인수인계가 됩니다.

회사에서 가장 진행되지 않는 업무가 인수인계라고 생각합니다. 문서로 모든 맥락을 전달하는 것도 어렵고, 담당자가 바뀔 때마다 충분한 시간을 확보하기도 쉽지 않습니다. 결국 가장 오래 남고 다음 사람이 반드시 마주하게 되는 것은 소스코드입니다. 따라서 변수와 함수의 이름만 보아도 역할을 짐작할 수 있고, 하나의 함수가 하나의 책임을 가지며, 복잡한 로직이 적절히 분리되어 있다면 코드 자체가 훌륭한 인수인계 자료가 될 수 있습니다. 별도의 설명이 없더라도 다음 개발자가 시스템의 의도와 흐름을 따라갈 수 있는 코드가 좋은 코드라고 생각합니다.

### 2. 당시의 Trade-Off를 설명하는 기준이 됩니다.

다음 사람이 읽기 좋은 소스코드는 당시 이 소스코드가 이렇게 구성될 수밖에 없었던 Trade-Off와 이에 대한 판단을 잘 표현합니다. 개발에는 항상 정답만 존재하지 않으며 성능, 일정, 복잡도, 확장성, 안정성 사이에서 선택해야 하는 순간이 있습니다. 좋은 코드는 이러한 선택의 결과가 구조적으로 드러나거나, 필요한 경우 주석과 문서를 통해 그 이유를 남깁니다. 그래야 다음 개발자가 단순히 "왜 이렇게 만들었지?"라고 생각하며 기존 코드를 다시 작성하는 것이 아니라, 당시의 제약과 판단을 이해한 뒤 현재 상황에 맞게 더 나은 결정을 내릴 수 있습니다.

### 3. 시간이 지날수록 좋은 동료들과 함께할 것입니다.

내가 대접받고 싶은 대로 남을 대접하는 황금률을 믿습니다. 내가 다른 사람의 코드를 읽을 때 이해하기 쉽고 수정하기 안전한 코드를 만나고 싶다면, 나 역시 다음 사람을 위해 그런 코드를 작성해야 한다고 생각합니다. 이런 태도가 팀 안에서 반복되면 자연스럽게 서로의 코드를 배려하고 리뷰하며 개선하는 문화가 만들어집니다. 결국 좋은 코드는 단순히 기술적인 결과물이 아니라 함께 일하는 사람에 대한 배려이며, 이러한 배려가 쌓일수록 서로 신뢰할 수 있는 좋은 동료들과 더 나은 개발 문화를 만들어갈 수 있다고 생각합니다.

# 질문2
## 현장 운영자로부터 "장치 하나가 몇 분 간격으로 OFFLINE과 ONLINE을 반복한다"는 보고를 받았습니다. 원인으로 의심되는 후보를 3가지 이상 제시하고 각 후보를 로그와 데이터로 확인하거나 배제하는 절차를 서술하세요.
OFFLINE과 ONLINE을 판단하는 기준은 last_heartbeat_time이며, 이에 대한 판단은 모니터링 쓰레드가 수행합니다. 따라서 우선 OFFLINE으로 변경된 시각과 당시의 last_heartbeat_time을 확인하여 실제로 30초 이상 하트비트가 갱신되지 않았는지 확인하겠습니다.
이후 정상적으로 하트비트가 생성되지 않은 것인지, 전송 과정에서 유실된 것인지, 백엔드까지 도착했으나 저장 또는 상태 판정에 문제가 있었던 것인지 확인하기 위해 장치 → 에이전트 → 백엔드 → 콘솔의 데이터 흐름을 따라 로그와 데이터를 비교하여 최초로 이상이 발생한 구간을 찾겠습니다.

### 1. 장치와 에이전트 사이의 연결이 반복적으로 끊기거나 메시지 송수신이 불안정한 경우
가장 먼저 의심할 것은 장치의 전원 문제, 시리얼 케이블 불량, USB 포트 문제, 네트워크 기반 장치라면 TCP 연결 불안정 등으로 인해 장치와 에이전트 사이의 연결이 주기적으로 끊기는 경우입니다.

특히 본 구현에서는 단순히 시리얼 연결이 존재하는 것만으로 장치가 살아 있다고 판단하지 않고, 장치로부터 실제 메시지를 수신했는지도 확인하므로 메시지 송수신 상태도 함께 확인해야 합니다. 장치 연결이 끊기면 SerialException이 발생하며 Agent는 재연결하도록 요구되어 있습니다. 

1) 장치 측 로그에서 DATA 등의 메시지를 정상 주기로 송신하고 있는지 확인합니다.
2) 동일 시간대의 에이전트 로그에서 해당 메시지를 정상적으로 수신하고 있는지 확인합니다.
3) 에이전트 로그에서 연결, 끊김, 재연결 등의 로그가 OFFLINE 발생 주기와 함께 반복되는지 확인합니다.
4) OFFLINE 직전에 장치 메시지가 중단되고 재연결 이후 다시 ONLINE으로 복구되는 패턴이 반복되는지 확인합니다.

장치와 에이전트 사이의 연결이 유지되고 메시지도 정상적으로 수신되고 있다면 이 후보는 배제할 수 있습니다.

### 2. 에이전트가 정상적으로 하트비트를 전송하지 못하는 경우
장치와 에이전트의 통신이 정상이라면 다음으로 에이전트의 하트비트 처리 과정을 확인하겠습니다.
에이전트 프로세스 또는 api_loop에 예외가 발생했거나, HTTP 요청을 장시간 처리하는 등의 이유로 하트비트가 예정된 주기대로 실행되지 않을 수 있습니다.

1) 에이전트 로그에서 하트비트가 설정된 주기에 맞게 실행되고 있는지 확인합니다.
2) api_loop의 예외나 HTTP 타임아웃 등의 로그가 존재하는지 확인합니다.
3) 같은 시간에도 device_loop에서 DATA를 정상적으로 수신하고 있는지 비교합니다.

장치 DATA는 계속 들어오지만 하트비트 로그만 중단된다면 장치 문제가 아니라 에이전트의 하트비트 처리 문제로 범위를 좁힐 수 있습니다.
반대로 에이전트에서 하트비트를 정상적으로 송신하고 있다면 다음으로 에이전트와 백엔드 사이 또는 백엔드 내부를 확인합니다.

### 3. 하트비트가 백엔드까지 정상적으로 전달되지 않는 경우
에이전트에서는 하트비트를 송신하고 있지만 백엔드에서 수신하지 못한다면 에이전트와 백엔드 사이의 네트워크 또는 백엔드 자체의 일시적인 장애를 의심할 수 있습니다.

1) 에이전트의 하트비트 송신 시각과 HTTP 응답 상태를 확인합니다.
2) 동일 시각의 백엔드 로그에서 하트비트가 수신되었는지 확인합니다.
3) 에이전트에서는 송신했으나 백엔드에 수신 로그가 없다면 네트워크 연결, 백엔드 프로세스 또는 컨테이너 상태 등을 확인합니다.
4) 에이전트의 하트비트 송신에서 타임아웃, 연결거부 등이 발생했고, 이것들이 OFFLINE 발생 주기와 일치하는지 확인합니다.

### 4. 백엔드가 하트비트를 받았지만 last_heartbeat_time 갱신 또는 상태 판정에 문제가 있는 경우
백엔드의 로그에서 하트비트 요청이 정상적으로 수신된 것이 확인된다면 다음으로 DB와 상태 판정 로직을 확인하겠습니다.

본 시스템에서는 마지막 하트비트가 30초 이내이면 ONLINE, 그렇지 않으면 OFFLINE으로 판단합니다. 따라서 다음 세 값을 같은 시점에 비교하겠습니다.
- 백엔드의 하트비트 수신 시각
- DB에 last_heartbeat_time를 갱신한 시각
- 모니터링 쓰레드가 상태를 판정한 시각

1) 하트비트를 수신한 후 last_heartbeat_time이 실제 DB에 갱신되는지 확인합니다.
2) UPDATE 이후 정상적으로 commit되었는지 백엔드 로그를 확인합니다.
3) 모니터링 쓰레드가 OFFLINE으로 변경한 시점의 last_heartbeat_time과 현재 시각 차이를 기록하여 실제로 30초를 초과했는지 확인합니다.

이같은 경우라면 장치나 네트워크 문제가 아니라 Backend 상태 판정 로직의 문제라고 판단할 수 있습니다.
